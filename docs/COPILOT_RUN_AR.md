## ١. التشغيل محلياً

### قاعدة البيانات

من جذر المستودع:

```bash
npm run docker:up
```

يشغّل حاوية Postgres من `docker-compose.yml` (المستخدم `npi`، المنفذ 5432، اسم الحاوية `npi-erp-postgres`). قاعدة NPI اسمها `npi_erp`؛ أما قاعدة مَدار `npi_copilot` فتُنشأ تلقائياً عند أول تشغيل (انظر الترحيلات أدناه).

### ملف البيئة

تُنسخ أسطر `apps/copilot/.env.example` إلى ملف **`.env` في جذر المستودع** وليس إلى `apps/copilot/.env` (التعليق الأول في ذلك الملف ينص على هذا). متغيرات NPI نفسها موجودة في الملف ذاته، ومَدار لا يقرأ منها شيئاً.

| المتغير | ما هو |
|---|---|
| `COPILOT_DATABASE_URL` | عنوان قاعدة مَدار؛ يجب أن ينتهي بـ`/npi_copilot`، وحارس قبل فتح أي اتصال يرفض أي اسم قاعدة آخر (حتى `npi_erp`) |
| `NPI_API_BASE` | عنوان واجهة NPI البرمجية؛ محلياً `http://localhost:4000/api` |
| `ANTHROPIC_API_KEY` | مفتاح مزوّد النماذج (Anthropic)؛ فارغ في الملف النموذجي ويجب أن تضعه أنت |
| `MADAR_PROVIDER` | القيمة الوحيدة المقبولة `anthropic` |
| `COPILOT_MODEL_ECONOMY` | النموذج الاقتصادي؛ الافتراضي `claude-haiku-4-5-20251001` |
| `COPILOT_MODEL_ADVANCED` | النموذج المتقدم؛ الافتراضي `claude-sonnet-5` |
| `COPILOT_SESSION_KEY` | مفتاح تشفير الجلسات: 32 بايتاً بصيغة ست عشرية (64 خانة). لا تولّده بيدك محلياً (انظر أدناه) |
| `COPILOT_DOCS_DIR` | مجلد المستندات المرفوعة؛ محلياً `./data/copilot_docs` |
| `COPILOT_DAILY_TOKEN_CAP` | سقف الرموز اليومي لكل مستخدم؛ الافتراضي 600000 |
| `COPILOT_PORT` | منفذ مَدار؛ الافتراضي 3100، وعلى جهازك 3110 لأن 3100 محجوز لحاوية مشروع آخر (قرار `D-10`) |
| `NEXT_PUBLIC_NPI_WEB_URL` | عنوان واجهة NPI للروابط بين التطبيقين؛ فارغ في الإنتاج (أصل واحد خلف Caddy)، و`http://localhost:3000` في التطوير |

**مفتاح الجلسة:** الأمر `npm run copilot:dev` يشغّل أولاً السكربت `apps/copilot/scripts/ensure-session-key.mjs`. هو يقرأ `.env` الجذر؛ فإن لم يجد سطر `COPILOT_SESSION_KEY` بقيمة غير فارغة أضاف سطراً بمفتاح عشوائي (32 بايتاً ست عشرية)، وإن وجده لم يفعل شيئاً. ولا يطبع قيمة المفتاح أبداً: يكتب فقط `session key present` أو `session key created`.

### التشغيل

```bash
npm run copilot:dev
```

يشغّل خادم NPI البرمجي ومَدار معاً، وكل سطر مسبوق باسم عمليته. افتح `http://localhost:<COPILOT_PORT>/copilot` (على جهازك `http://localhost:3110/copilot`). الدخول بحسابات NPI نفسها: حساب مدير العرض `admin@npi.sa` وكلمة مروره المعلنة في `deploy/README_AR.md` §5.

### الترحيلات

```bash
npm run copilot:migrate
```

يعادل `prisma migrate deploy` على `npi_copilot`، وإذا لم تكن القاعدة موجودة أنشأها أولاً.

### الاختبارات

كلها من داخل `apps/copilot` (وليس بـ`npm test` من الجذر):

| الأمر | ماذا يفعل |
|---|---|
| `npx jest` | الاختبارات الوحدوية والبنيوية |
| `npx playwright test` | اختبار النهاية إلى النهاية على سطح المكتب والجوال. يشغّل بنفسه واجهة NPI البرمجية على المنفذ 4077 ومَدار على 3177، فوق **نسخة خاصة** من قاعدتك اسمها `npi_erp_e2e` يصنعها السكربت `packages/db/prisma/madar-e2e-db.mjs` (ولتحديثها `--refresh`) حتى لا تقرأ قاعدة NPI المشتركة صفوف فرع آخر |
| `npm run perf` | بوابة الأداء: يبني النسخة الإنتاجية ويقيس كل شاشة على جهاز مكتبي وهاتف محاكى؛ يحتاج واجهة NPI البرمجية شغّالة على المنفذ 4000، ويكتب تقريره في `apps/copilot/perf-results/` |
| `npm run eval:extract` | قياس دقة قراءة المستندات (35 مدخلاً) بالنموذج الحقيقي |
| `npm run eval:behaviour` | السلوكيات العشرون في `06` §3 بالنموذج الحقيقي وبواجهة NPI المحلية |
| `npm run eval:pii` | قياس بوابة إخفاء الأسماء على 100 جملة؛ بلا نموذج ولا شبكة |
| `npm run eval:memory` | قياس الذاكرة المشتقة من بيانات NPI؛ بلا نموذج |

وللتحضير فقط: `npm run eval:extract:photos` و`npm run eval:extract:scans` يبنيان صور التقييم وملفاته الممسوحة من مصادرها.

**تنبيه:** أمرا `eval:extract` و`eval:behaviour` يستدعيان النموذج الحقيقي، فيُحسب استهلاكهما على السقف اليومي (`COPILOT_DAILY_TOKEN_CAP`) وعلى رصيد المفتاح. التشغيل الكامل الواحد لـ`eval:extract` استهلك 401,448 رمزاً من 600,000، فالثاني في اليوم نفسه يحتاج رفع السقف للعملية (طريقته في `docs/COPILOT_EVAL_AR.md` §٦). وكذلك الأمران `e2e:live-setup` و`e2e:live-flows` (يعملان بالنموذج الحقيقي ويُفعَّلان بمتغير لا يُضبط إلا بهما).

**تنبيه آخر:** اختبار النهاية إلى النهاية يحذف جلسة التأسيس المفتوحة للمنشأة قبل كل اختبار؛ لا تشغّله على قاعدة يعمل عليها مدير النظام الآن.

## ٢. النشر على خادم العرض

المراجع: `deploy/README_AR.md`، `deploy/deploy.sh`، `deploy/.env.example`، `docker-compose.prod.yml` (الخدمة `copilot`)، `deploy/Caddyfile`.

### ما يُنشر

مَدار حاوية مستقلة (`npi-erp-copilot`) في حزمة الإنتاج نفسها خلف Caddy. بيئتها خاصة بها: لا `env_file`، ولا عنوان قاعدة NPI، ولا سر توقيع NPI. تصل إلى NPI عبر HTTP فقط وبصفة المستخدم المسجّل، ولها قاعدة `npi_copilot` على حاوية Postgres نفسها وحجم `copilot_docs` للمستندات المرفوعة.

### الخطوات

1. **على جهازك (ويندوز)** من جذر المستودع:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\pack.ps1
scp npi-erp-deploy.tar.gz root@SERVER_IP:/opt/
```

2. **على الخادم:** فكّ الحزمة في `/opt/npi-erp`:

```bash
cd /opt && mkdir -p npi-erp && tar -xzf npi-erp-deploy.tar.gz -C npi-erp && cd npi-erp
```

3. **الأسرار:** في `deploy/.env` (من `deploy/.env.example`) متغيران خاصان بمَدار: `ANTHROPIC_API_KEY` و`COPILOT_SESSION_KEY` (ولّده بأمر `openssl rand -hex 32`، مستقلاً عن سر NPI). **بدونهما يرفض `docker compose` تشغيل الخدمة** ويسمّي المتغير الناقص. والاختياري المعلَّق في الملف: `COPILOT_MODEL_ECONOMY` و`COPILOT_MODEL_ADVANCED` و`COPILOT_DAILY_TOKEN_CAP`.

4. **التشغيل الأول على خادم جديد** (الخطوة 5 من `deploy/README_AR.md`): `docker compose -f docker-compose.prod.yml --env-file deploy/.env up -d --build`. أما `deploy.sh` فيحدّث حزمة حيّة ولا يصلح للتثبيت الأول.

5. **كل نشر لاحق:**

```bash
sh deploy/deploy.sh
```

وهذا ما يفعله بالترتيب:

| # | الخطوة |
|---|---|
| ١ | بناء صور `api` و`web` و`copilot`، ووسمها برقم الإيداع (أو بالتاريخ والوقت إن لم يوجد `git`)؛ هذا ما يعود إليه التراجع |
| ٢ | ترحيل قاعدة `npi_erp` والنسخة القديمة ما زالت تخدم |
| ٣ | ترحيل قاعدة `npi_copilot` بأداة Prisma الموجودة في صورة مَدار، وقبل أي تبديل |
| ٤ | تبديل `api` ثم `web` ثم `copilot`: تبدأ الحاوية الجديدة بجوار القديمة، وتُسحب القديمة بعد نجاح فحص صحة الجديدة |
| ٥ | خادم لم يشغّل مَدار من قبل: يبدأ `copilot` للمرة الأولى بدل تبديله |
| ٦ | إعادة تحميل مسارات Caddy من `deploy/Caddyfile` (الحزمة الجديدة تستبدل الملف على الخادم بملف جديد لا تتبعه الحاوية، فيُسلَّم المحتوى إلى Caddy عبر واجهته الإدارية) |
| ٧ | التحقق عبر Caddy نفسه (طريق المستخدم الفعلي) من `/api/health` ومن `/copilot/api/health`؛ كلاهما يجب أن يعطي 200 |

إن فشل الترحيل في الخطوة ٢ أو ٣ توقف النشر قبل أي تبديل وبقيت النسخة القديمة تخدم.

6. **معاينة بلا تنفيذ:** `sh deploy/deploy.sh --dry-run` يطبع الخطة فقط ولا يشغّل أي أمر Docker.

7. **التراجع:** `sh deploy/deploy.sh --rollback` يعيد الصور الموسومة بالنسخة السابقة. **لا يتراجع عن الترحيلات** (قاعدة التوافق مع النسخة السابقة هي ما يجعل هذا آمناً). وصورة مَدار لا تُعاد إلا إذا كانت النسخة السابقة تحمل واحدة؛ وإلا بقي مَدار على نسخته الحالية وكُتب هذا في السجل.

### الرابط والسجلات

- الرابط: `https://<SITE_ADDRESS>/copilot` (قيمة `SITE_ADDRESS` من `deploy/.env`).
- سجلات مَدار:

```bash
docker compose -f docker-compose.prod.yml --env-file deploy/.env logs -f copilot
```

## ٣. النسخ الاحتياطي والاستعادة

المرجع: `deploy/backup.sh` (التعليقات في رأسه هي إجراء الاستعادة الكامل) و`deploy/README_AR.md` §8.

### التثبيت

سطر الجدولة اليومية (الثانية فجراً) على الخادم:

```
0 2 * * * cd /opt/npi-erp && sh deploy/backup.sh >> /var/log/npi-backup.log 2>&1
```

### ماذا يُكتب كل ليلة

ثلاثة ملفات في `/opt/npi-erp/backups` (يُغيَّر بمتغير `BACKUP_DIR`):

| الملف | محتواه |
|---|---|
| `npi_erp_<stamp>.dump` | قاعدة NPI |
| `npi_copilot_<stamp>.dump` | قاعدة مَدار |
| `copilot_docs_<stamp>.tar.gz` | المستندات المرفوعة من حجم `copilot_docs` |

كل ملف يُفحص بعد كتابته (حجم لا يقل عن 10 كيلوبايت، ثم `pg_restore --list` للقواعد و`tar -tzf` للأرشيف)، ويُحتفظ بأحدث 14 من كل نوع (يُغيَّر بمتغير `KEEP`). على خادم لم يُنشر عليه مَدار بعد يُسجَّل سطر «تم التخطي» ولا يُعدّ فشلاً. وللنسخ خارج الخادم يُضبط `OFFSITE_CMD` وينفَّذ مرة لكل ملف. و`sh deploy/backup.sh --dry-run` يطبع ما سيُكتب بلا تنفيذ.

### قاعدة الاستعادة

**استعد الجانبين من الليلة نفسها.** صفوف مَدار تشير إلى معرّفات NPI (المنشأة والمستخدمون والعملاء…)، فنسخة مَدار الأقدم من نسخة NPI تصف مستندات ومهام لا يعرفها NPI. واستعادة NPI نفسها مكتوبة خطوة بخطوة في رأس `deploy/backup.sh` (أوقف `api` و`web`، أعد إنشاء القاعدة، `pg_restore`، الترحيلات، التحقق، ثم التشغيل). وفيما يلي استعادة مَدار بترتيبها، كما في السكربت؛ ونفّذها بعد أن يكون `C` معرَّفاً:

```bash
C=" -f docker-compose.prod.yml --env-file deploy/.env"

# 1. اختر أحدث نسخة صراحة
DUMP=$(ls -1t /opt/npi-erp/backups/npi_copilot_*.dump | head -1); echo "$DUMP"
DOCS=$(ls -1t /opt/npi-erp/backups/copilot_docs_*.tar.gz | head -1); echo "$DOCS"

# 2. اثبت أن الملفين مقروءان قبل أن تهدم أي شيء
pg_restore --list "$DUMP" > /dev/null || { echo "UNREADABLE DUMP"; exit 1; }
tar -tzf "$DOCS" > /dev/null || { echo "UNREADABLE DOCS ARCHIVE"; exit 1; }

# 3. أوقف مَدار (NPI يبقى شغّالاً)
docker compose $C stop copilot

# 4. أعد إنشاء القاعدة فارغة
docker compose $C exec -T postgres \
  sh -c 'dropdb -U npi --force npi_copilot && createdb -U npi npi_copilot'

# 5. استعد
docker compose $C exec -T postgres \
  pg_restore -U npi -d npi_copilot --no-owner --exit-on-error < "$DUMP"

# 6. المستندات: أفرغ الحجم ثم فكّ الأرشيف فيه
docker compose $C run --rm --no-deps --entrypoint sh copilot \
  -c 'find /data/copilot_docs -mindepth 1 -delete'
docker compose $C run --rm --no-deps --entrypoint sh -T copilot \
  -c 'tar -xzf - -C /data/copilot_docs' < "$DOCS"

# 7. أي ترحيلات أحدث من النسخة، ثم شغّل
docker compose $C run --rm --no-deps copilot \
  node node_modules/prisma/build/index.js migrate deploy --schema apps/copilot/prisma/schema.prisma
docker compose $C start copilot

# 8. تحقق: الأعداد تطابق أرقام تلك الليلة، ولكل مستند مخزَّن ملفه
docker compose $C exec -T postgres psql -U npi -d npi_copilot -c \
  'SELECT (SELECT count(*) FROM documents) AS documents,
          (SELECT count(*) FROM intake_jobs) AS intake_jobs,
          (SELECT count(*) FROM llm_audit) AS llm_audit;'
docker compose $C exec -T copilot sh -c 'find /data/copilot_docs -type f | wc -l'
```

لماذا الخطوة ٦ مهمة: مَدار يرفض مستنداً ملفه مفقود، فقاعدة مستعادة بلا ملفاتها نصف استعادة، وتظهر في المحادثة كأخطاء «غير موجود». **اختبر الاستعادة فور التثبيت**؛ نسخة لم تُجرَّب ليست نسخة احتياطية.

## ٤. التصفير الليلي لخادم العرض

> ⚠️ **لخوادم العرض فقط.** هذه المهمة تمسح قواعد البيانات. هي في ملف مستقل (`deploy/docker-compose.demo-reset.yml`) حتى لا يصل إليها أمر مكتوب على ملف الإنتاج بالخطأ. **لا تُثبّتها أبداً على خادم يحمل بيانات حقيقية.**

فيه مهمتان **مستقلتان عمداً** (فشل إحداهما لا يمنع الأخرى):

| المهمة | ماذا تفعل |
|---|---|
| `demo-reset` | تصفّر قاعدة NPI بالكامل وتعيد الترحيلات والبيانات التجريبية |
| `demo-reset-copilot` | تُسقط قاعدة `npi_copilot` وتنشئها من جديد وتعيد ترحيلاتها، وتفرغ حجم المستندات `copilot_docs` فلا يبقى مستند يتيم. **بلا بيانات أولية:** تبدأ المنشأة الصباح من شاشة «التأسيس» من جديد |

سطر الجدولة (الثالثة فجراً بتوقيت الرياض) كما في `deploy/README_AR.md` §7، ويشغّل المهمتين معاً:

```
0 3 * * * cd /opt/npi-erp && docker compose -f docker-compose.prod.yml -f deploy/docker-compose.demo-reset.yml --env-file deploy/.env run --rm demo-reset >> /var/log/npi-reset.log 2>&1; docker compose -f docker-compose.prod.yml -f deploy/docker-compose.demo-reset.yml --env-file deploy/.env run --rm demo-reset-copilot >> /var/log/npi-reset.log 2>&1
```

وتأكد من توقيت الخادم: `timedatectl set-timezone Asia/Riyadh`. ولتصفير مَدار وحده يدوياً: الأمر نفسه بالمهمة `demo-reset-copilot` فقط.

## ٥. سياسة الموافقة على إرسال الصور

القرار المسجَّل (`spec/madar/10-RISKS-AND-ASSUMPTIONS.md` §٨ القرار 3): المستندات النصية بإخفاء محلي، والصور تُرسل بموافقة صريحة مسجّلة، و«سري» لا يُرسل.

| نوع المدخل | ما يحدث |
|---|---|
| ملف PDF نصي | يُستخرج نصه ويُخفي مَدار الأسماء والمعرّفات **محلياً** (البوابة نفسها لكل نص)؛ لا يغادر إلا النص المُخفى بعلامات بديلة |
| صورة، أو PDF ممسوح ضوئياً | لا يمكن إخفاء الأسماء فيه، فلا يُرسل إلا بعد أن يضغط المستخدم «اعتمد الإرسال» على بطاقة الموافقة |
| مستند موسوم «سري» | لا يُرسل إلى أي نموذج أبداً |

**بطاقة الموافقة** كما تظهر للمستخدم:

- العنوان: «سيُرسل هذا المستند كصورة إلى مزوّد النماذج».
- النص: «لا يمكن إخفاء الأسماء في الصور قبل الإرسال. {سطر السياسة} سيُسجَّل هذا الإرسال في سجل الثقة.»
- سطر السياسة، حرفياً كما يُخزَّن مع كل موافقة: «سياسة المزوّد: لا تُستخدم المدخلات والمخرجات لتدريب النماذج افتراضياً (تم التحقق منها بتاريخ 2026-09-21).»
- ما سيُرسل: «ما سيُرسل: صورة واحدة»، أو عدد الصفحات كصور للملف الممسوح.
- الزران: «اعتمد الإرسال» و«ألغِ».

**السجل:** كل موافقة تُسجَّل برقم، وهذا الرقم يُخزَّن ويظهر في شاشة الثقة `/copilot/trust` (لمدير النظام وحده) في عمود «رقم الموافقة» لكل إرسال صورة. والسطر الأعلى في الشاشة يحسب على السجل كله: «كل إرسال صورة مسجَّل برقم موافقة»، وإن وُجد خلافه عرض «إرسالات صور بلا رقم موافقة: {العدد}». والإرسال بلا رقم موافقة ممنوع في الكود وفي قاعدة البيانات معاً.

**المستند «السري»:** يُرفض إن وردت إحدى الكلمات «سري» أو «سرية» أو `confidential` ككلمة كاملة (فلا تُحجب «سرير» ولا «سريع») في اسم الملف، أو في أول 2000 حرف من نص الـPDF النصي. والرفض يظهر هكذا: «هذا المستند موسوم «سري» ولن يُرسل إلى أي نموذج خارجي. يمكنك إدخاله من شاشة NPI.» **حدّ يجب أن تعرفه:** الصورة والملف الممسوح بلا طبقة نصية لا يُقرأ محتواهما، فلا يُفحص منهما إلا **اسم الملف**؛ لذلك سمِّ المستند السري باسم يحمل الكلمة، أو لا ترفعه.

**الإملاء الصوتي (القرار `D-22`):** زر الميكروفون على الجوال يستخدم خدمة التعرف على الكلام في المتصفح نفسه، لا مَدار ولا مزوّد النماذج. في كروم (مكتبي وأندرويد) يذهب الصوت إلى خدمة غوغل، وفي سفاري إلى آبل، وفي فايرفوكس لا توجد الخدمة. مَدار لا يستقبل الصوت ولا يطلب أي خدمة بنفسه؛ الكلمات تظهر في صندوق الكتابة **مسودة** تراجعها، ولا يُرسل شيء حتى تضغط إرسال، ثم تُعامَل كالنص المكتوب (إخفاء الأسماء ثم الرد). يبدأ الإملاء بضغطة صريحة ويظهر سطر «أستمع… تحدّث الآن، وراجع النص قبل الإرسال.» طوال عمله. لكن الصوت نفسه، وقد يتضمن اسم عميل أو مبلغاً، يغادر الجهاز عبر مزوّد المتصفح لا عبر المزوّد الذي تحققنا من سياسته. الوضع الحالي: الإبقاء عليه، والقرار `D-22` ما زال **مفتوحاً** في `PROGRESS.md` ينتظر حكمك (البديل إخفاء الميكروفون).

## ٦. ماذا تفعل حين يرفض NPI

مَدار لا يكتب في NPI إلا بصفة المستخدم نفسه وبصلاحياته، فإذا رفض NPI أمراً وصلتك رسالة عربية ثابتة (وقد يُلحق بها NPI سببه بنصه الأصلي بين قوسين). الجدول مأخوذ من `apps/copilot/src/npi/errors.ts`:

| الرسالة التي تراها | معناها | ما تفعله |
|---|---|---|
| «انتهت جلستك في NPI. سجّل الدخول من جديد.» | رمز الدخول منتهٍ أو غير صالح | سجّل الدخول من جديد |
| «NPI رفض: ليست لك صلاحية تنفيذ هذا الإجراء.» | دور المستخدم في NPI لا يحمل الصلاحية | يعدّل مدير النظام صلاحية الدور من شاشة `/admin` في NPI، ثم أعد المحاولة |
| «NPI رفض: السجل غير موجود أو لا يخص منشأتك.» | السجل لمنشأة أخرى أو محذوف | **لم يُنشأ شيء.** راجع الرقم أو اختر السجل الصحيح |
| «NPI رفض: تعارض مع حالة السجل الحالية.» | تغيّرت حالة السجل في NPI منذ قرأه مَدار | افتح السجل في NPI وانظر حالته، وأكمل منه أو أعد البدء |
| «NPI رفض: البيانات غير مقبولة.» | حقل لا يقبله NPI | صحّح الحقل على البطاقة ثم أعد الإرسال |
| «تعذر إتمام الطلب في NPI حالياً.» | خطأ في خادم NPI | أعد المحاولة بعد قليل؛ إن تكرر فانظر سجلات `api` (أدناه) |
| «NPI لم يستجب خلال المهلة.» | تأخر الرد | كالسابق |
| «تعذر الوصول إلى NPI.» | تعذر الاتصال | كالسابق، وتحقق من فحص الصحة (§٧) |
| «استجابة غير متوقعة من NPI.» | رمز حالة لا يعرفه مَدار | أبلغ المطوّر مع وقت الحدث |

سجلات واجهة NPI:

```bash
docker compose -f docker-compose.prod.yml --env-file deploy/.env logs -f api
```

**القواعد التي لا تتغير:**

- **مَدار لا يعتمد شيئاً.** الاعتماد من صندوق الاعتمادات في NPI وحده، ولا تجاوز لمصفوفة الاعتمادات بلا استثناء (قرارك المسجَّل). وما يترك مَدار تنفيذه على المستخدم يُكتب على البطاقة «يدوياً في NPI» (تفعيل العقد، اعتماد أمر الشراء، فحص الاستلام، المطابقة الثلاثية).
- **مَدار لا يحذف شيئاً** من NPI، ولا يمحو ما أنشأه إن فشلت خطوة لاحقة.
- **التنفيذ الجزئي:** إن نجح إنشاء العميل وفشل العقد مثلاً، فبطاقة التنفيذ تعدّد ما أُنشئ فعلاً وتتوقف عند أول رفض بنص NPI؛ **أكمل الباقي من NPI نفسه**. لا حذف آلي ولا إعادة محاولة تلقائية (الخطر `R-02` في `spec/madar/10-RISKS-AND-ASSUMPTIONS.md`).
