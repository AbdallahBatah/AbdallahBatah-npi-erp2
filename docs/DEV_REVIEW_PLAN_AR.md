# المراجعة التطويرية الشاملة وخطة التطوير — NPI Solar ERP

**التاريخ:** 2026-07-29
**المنهجية:** 4 مراجعات معمّقة متوازية للكود الفعلي (البنية الخلفية NestJS — نموذج البيانات Prisma — الواجهة الأمامية Next.js — الجوانب المقطعية: اختبارات/أمان/تشغيل/أداء)
**الحجم الحالي:** ~6,800 سطر API عبر 66 ملفاً و103 نقطة نهاية، ~9,000 سطر واجهة عبر 24 صفحة، 51 جدولاً و42 تعداداً في قاعدة البيانات، 8 هجرات.

---

## 1. الخلاصة التنفيذية

النظام اليوم **شريحة رأسية ممتازة لقطاع الطاقة الشمسية** — دورة حياة كاملة من العميل المحتمل حتى الفوترة الإلكترونية (ZATCA) والاعتراف بالإيراد (IFRS-15) وتسويات PPA — لكنه **ليس منصة** بالمعنى الذي تمثله أودو. المسافة بين الوضع الحالي وبين «نظام مرن متكامل يحاكي أودو» مسافة **معمارية** وليست تراكم مزايا، وتتلخص في أربعة غيابات حاملة:

1. **لا طبقة بيانات وصفية (Metadata Layer):** الضرائب، وخريطة الحسابات، وسلاسل الترقيم، وقواعد سير العمل، وحدود التنبيهات — كلها ثوابت مُجمّعة في الكود لا بيانات قابلة للضبط لكل منشأة. أودو يجعل كل هذا «إعدادات».
2. **لا طبقة أحداث/جدولة:** لا شيء يحدث دون طلب HTTP يدوي. لا يوجد event bus ولا طوابير ولا مجدول — حتى توليد أوامر الصيانة الوقائية زر يُضغط يدوياً.
3. **عزل المستأجرين يدوي:** ~250 موضعاً يكتب `organizationId` يدوياً في كل استعلام؛ كل تعديل قادم فرصة تسريب بين المستأجرين. و10 جداول بلا `organizationId` أصلاً.
4. **لا شبكة أمان هندسية:** **صفر اختبارات، لا مستودع Git، لا CI، لا نسخ احتياطي آلي** — على نظام مالي يحرّك قيوداً وفواتير ضريبية. أي إعادة هيكلة نحو المنصة غير آمنة قبل معالجة هذا.

**نقاط القوة الحقيقية التي يجب الحفاظ عليها:** انضباط `organizationId` شبه الكامل، صفر SQL خام (لا سطح حقن)، معاملات ذرّية سليمة حول القيود المالية، تحقق صارم من المدخلات (ValidationPipe + whitelist)، 110 فهرس مدروس، ثنائية اللغة RTL من الطراز الأول، توثيق داخلي صادق (بذور ZATCA المحاكاة معلَّمة بوضوح).

**التوصية:** خطة من 5 مراحل تبدأ بشبكة الأمان (لا يجوز تأجيلها)، ثم بناء «نواة المنصة»، ثم استكمال جوهر ERP، ثم مرونة أودو (سير عمل، حقول مخصصة، طرق عرض)، ثم الجاهزية الإنتاجية والتوسع.

## 2. نتائج المراجعة بالتفصيل

### 2.1 البنية الخلفية (NestJS)

| المحور | الحالة | التفصيل |
|---|---|---|
| تقسيم الوحدات | 🟡 | 10 وحدات نظيفة شكلياً، لكن خدمتين تحملان ربع المنطق: `procurement.service` (878 سطراً) و`fsm.service` (802) — خدمات-إله تلمس 13–18 جدولاً خارج نطاقها وتُرحّل قيوداً محاسبية بنفسها |
| الترابط | 🔴 | لا استيراد مباشر بين الوحدات (جيد)، لكن الترابط كامل عبر قاعدة البيانات: `ppa.service` ينشئ فواتير مباشرة مكرراً منطق الفوترة وحساب الضريبة؛ الحدود اتفاقية لا معمارية |
| الأحداث والجدولة | 🔴 | لا يوجد أي منها: لا event-emitter، لا BullMQ، لا @nestjs/schedule. الصيانة الوقائية والتنبيهات تعتمد على نقر بشري |
| الصلاحيات | 🟡 | `JwtAuthGuard` عام (جيد)، لكن `PermissionsGuard` انضمامي لكل متحكم — والنتيجة ثغرة فعلية: `reference.controller` بلا حارس يكشف قيمة خط الأنابيب وأسعار التسعير لأي مستخدم مصادق. أي متحكم جديد يفشل مفتوحاً |
| الترقيم المتسلسل | 🔴 | `NumberingService.next` يقرأ ثم يحدّث في خطوتين غير ذرّيتين — تعارض متزامن يمكن أن يكرر رقم فاتورة (خطر ZATCA مباشر) |
| معالجة الأخطاء | 🔴 | لا ExceptionFilter ولا رموز أخطاء؛ رسائل إنجليزية حرة تُترجم في الواجهة بـ 27 تعبيراً نمطياً regex — نمط هش سينكسر مع كل رسالة جديدة |
| التحقق | 🟢 | ValidationPipe عام صارم؛ استثناء وحيد: وحدة المالية بلا `dto.ts` — مبالغ الدفعات **غير مُتحقَّق منها** |
| التوثيق الآلي | 🔴 | لا Swagger/OpenAPI؛ كتالوج النقاط مكتوب يدوياً في README وسينحرف |

### 2.2 نموذج البيانات (Prisma)

**قوي:** 61 فهرساً + 49 قيد فرادة متطابقة تماماً مع الهجرات (لا انحراف)؛ دقة Decimal مدروسة (لا float إطلاقاً)؛ مفاتيح طبيعية على مستوى المستأجر `(organizationId, code)` في 28 جدولاً؛ قواعد الحذف التتالي مقصودة ومتسقة.

**المخاطر البنيوية المرتبة بالأثر:**

1. **`SettlementRun` بلا قيد فرادة على الفترة** — لا شيء يمنع تسوية نفس فترة PPA مرتين = **فوترة إيراد مكررة**. (الأعلى خطراً)
2. **حذف صف `Organization` يمسح المستأجر كاملاً بالتتالي** بما فيه سجلات ZATCA والقيود الملزمة قانونياً بالاحتفاظ — لا soft-delete ولا قيد حماية.
3. **`EInvoiceDocument` بلا `organizationId`** وسلسلة PIH تُرتَّب بـ `submittedAt` (زمن قابل للتعادل) بدل عدّاد رتيب — هشاشة في سلسلة تشفيرية نظامية.
4. **سند القبض مربوط بفاتورة واحدة إلزاماً** — تحويل بنكي واحد يسدد 3 فواتير لا يمكن تسجيله؛ لا توزيع دفعات ولا رصيد تحت الحساب.
5. **الإشعار الدائن `CREDIT_NOTE` قيمة تعداد بلا نموذج بيانات** — لا `originalInvoiceId` (مرجع إلزامي في ZATCA) ولا أي كود يعالجه.
6. **15 حقلاً بهيئة مفتاح أجنبي بلا قيد مرجعي** (`approvedById`, `parentWbsId`, `sourceId`...) — شجرة WBS يمكن أن تحوي دورات وأيتاماً.
7. **علاقات 1:1 خانقة:** عقد↔مشروع (مشروع ثانٍ لنفس العقد مستحيل)، عقد↔تعرفة PPA (لا تعديل تعرفة تاريخي)، مستخلص↔فاتورة (لا فوترة جزئية)، احتجاز↔إفراج واحد (لا إفراج على دفعات).
8. **قوائم التحقق JSON بدل جداول** — دليل الصيانة الوقائية القابل للتدقيق غير قابل للاستعلام أو التقارير.
9. **تعدادات Postgres لما يجب أن يكون جداول مرجعية:** `ItemCategory`, `AssetType`, `CostType` — إضافة فئة منتج جديدة = هجرة ونشر.
10. **الطوابع الزمنية متفاوتة:** 34 نموذجاً بلا `@updatedAt` بينها نماذج متحولة الحالة.

**الغائب كلياً من مخطط البيانات:** المرفقات/المستندات، الإشعارات، الموارد البشرية، أسعار الصرف، الفترات المالية والإقفال، الحسابات البنكية والتسوية البنكية، قوائم الأسعار، وحدات القياس وتحويلاتها، تتبع الدفعات (lot)، متغيرات المنتجات، عناوين وجهات اتصال متعددة للعملاء والموردين، الحقول المخصصة.

### 2.3 الواجهة الأمامية (Next.js)

| المحور | الحالة | التفصيل |
|---|---|---|
| طبقة البيانات | 🔴 | لا SWR ولا React Query — `useEffect + useState` مكرر في 21 من 22 صفحة؛ لا كاش ولا إلغاء تكرار ولا تحديث خلفي؛ كل تحويل يعيد الجلب كاملاً |
| مكوّنات مشتركة | 🔴 | لا يوجد `DataTable` ولا `FilterBar` ولا `Select/DatePicker/Tabs` — 35 جدولاً مكتوبة يدوياً، 19 نافذة Modal بترويسات مكررة، منطق الترقيم الصفحي منسوخ 3 مرات |
| مشاركة الأنواع | 🔴 | **صفر** مشاركة مع الخلفية: ~86 interface محلية، `Project` معرّف 5 مرات بأشكال متباينة؛ `packages/shared` لا تُستورد في الويب إطلاقاً — حتى مفاتيح الصلاحيات نصوص خام قابلة للخطأ الصامت |
| النماذج | 🔴 | لا مكتبة نماذج ولا تحقق حقلي؛ 8 خصائص `required` فقط في التطبيق كله؛ الأخطاء تظهر Toast فقط دون تعليم الحقل |
| حجم الصفحات | 🟡 | `projects/[id]` = 621 سطراً بـ 18 useState و6 جداول ونافذتين في دالة واحدة؛ `procurement` = 23 useState |
| تقييد الصلاحيات | 🔴 | `can()` تُستدعى في **موضع واحد** (روابط القائمة الجانبية فقط)؛ كل الأزرار مرئية للجميع والاكتشاف بالفشل (403)؛ الصفحات المخفية تفتح بكتابة العنوان |
| i18n | 🟡 | 494 مفتاحاً لكل لغة بتكافؤ تام (جيد)، لكن: مفاتيح غير منمّطة (typo يعرض المفتاح الخام)، لا interpolation ولا جمع، النصوص المترجمة موزعة على 6 ملفات |
| RTL | 🟢 | الأقوى في الكود: خصائص CSS منطقية متسقة، dir من الخادم بلا وميض، أرقام لاتينية مثبتة، خط ذاتي الاستضافة |
| الحماية | 🔴 | JWT في localStorage (قابل للسرقة عبر XSS)؛ لا `middleware.ts` — الحماية عميلية فقط وكل JS الصفحات يصل لغير المصادقين |

**الغائب مقارنة بواجهة أودو:** بحث شامل، فرز الأعمدة (صفر جداول قابلة للفرز)، مرشحات محفوظة/URL، تحديد متعدد وإجراءات جماعية، عرض كانبان (رغم وجود مراحل الفرص!)، تقويم/Gantt، تصدير (صفحة واحدة فقط)، مركز إشعارات، سجل نشاط على السجلات (سجل التدقيق يُكتب ولا يُقرأ!)، طباعة/PDF (حتى الفاتورة غير قابلة للطباعة)، مرفقات، **أي شاشة إعدادات على الإطلاق** (لا مستخدمون ولا أدوار ولا شجرة حسابات ولا ضرائب — كلها بذور فقط)، ملف شخصي/تغيير كلمة مرور، وضع داكن.

### 2.4 الجودة والأمان والتشغيل

**الأخطر أولاً:**

1. 🔴 **لا Git إطلاقاً** — لا تاريخ ولا تراجع ولا فروع. أول إجراء في الخطة.
2. 🔴 **صفر اختبارات + صفر CI** على منطق مالي (ضريبة، قيود، اعتراف إيراد، تسويات).
3. 🔴 **لا نسخ احتياطي آلي**، والأدهى: خدمة `reset` بـ `migrate reset --force` في نفس ملف compose الإنتاجي وبتوصية cron ليلي — خطأ نسخ واحد يمحو بيانات حقيقية بلا استرجاع.
4. 🔴 **تسجيل الدخول بلا أي تقييد معدل** + فشل الدخول لا يُسجَّل في التدقيق = حشو بيانات اعتماد غير مرئي وغير محدود، وDoS رخيص عبر bcrypt.
5. 🔴 **سر JWT الاحتياطي مكتوب في الكود** والحارس يفحص الوجود لا القيمة؛ `.env` المحلي ما زال يحمل القيم النموذجية داخل مجلد OneDrive متزامن.
6. 🟡 **سجل التدقيق ناقص وغير مقروء:** تعديل أسعار الأصناف (أساس كل تسعير لاحق) بلا تدقيق، تيليمتري تسويات PPA بلا تدقيق، ولا يوجد أي endpoint أو شاشة لقراءة السجل — يناقض الوعد الامتثالي للنظام.
7. 🟡 **الترقيم الصفحي غائب في 37 من 40 قائمة** + `telemetry/ingest` بلا حد لحجم المصفوفة (10,000 قراءة = ~30,000 استعلام متسلسل).
8. 🟡 **لا رصد إطلاقاً:** سطرا log في التطبيق كله، لا `/health` حقيقي (فحص TCP لا يكشف قاعدة بيانات ميتة)، اللوجات تفنى مع الحاوية.
9. 🟡 لا helmet، لا حد لحجم الطلب، `bcryptjs` بكلفة 10 (دون توصية OWASP)، رسالة 403 تسرد مفاتيح الصلاحيات الناقصة.

## 4. خطة التطوير — خمس مراحل

> المبدأ الحاكم: **لا إعادة هيكلة قبل شبكة الأمان (M0)، ولا مزايا منصة قبل النواة (M1).** كل مرحلة تُسلَّم خضراء قبل التالية.

### المرحلة M0 — شبكة الأمان الهندسية (أسبوع–أسبوعان) 🚨

الهدف: جعل أي تغيير لاحق آمناً وقابلاً للتراجع.

1. **Git فوراً**: `git init` + أول commit + مستودع بعيد خاص (GitHub) + حماية الفرع الرئيسي.
2. **CI (GitHub Actions)**: typecheck + lint + build + اختبارات على كل push؛ إضافة ESLint + Prettier فعليين.
3. **بنية اختبارات**: Jest + Testing Module في `apps/api`؛ البدء بالمنطق المالي الحرج: حساب الضريبة، توازن القيود، سلسلة PIH، الترقيم المتزامن (اختبار سباق)، تسوية PPA، الاعتراف بالإيراد. هدف أولي: ~60 اختباراً تغطي كل مسار مالي.
4. **نسخ احتياطي آلي**: cron يومي `pg_dump` + رفع خارج الخادم (S3/B2) + **توثيق واختبار الاسترجاع** + نقل خدمة `reset` إلى ملف compose منفصل بعيداً عن الإنتاج.
5. **سد الثغرات الفورية** (كلها تغييرات صغيرة):
   - `@nestjs/throttler` على مستوى التطبيق + تشديد على `/auth/login`؛ تسجيل محاولات الدخول الفاشلة في التدقيق.
   - جعل `PermissionsGuard` عاماً (fail-closed) + صلاحيات صريحة لـ `reference.controller`.
   - إزالة السر الاحتياطي `change-me...` نهائياً (فشل الإقلاع دون سر بأي بيئة) + فحص القيمة لا الوجود.
   - helmet + حد حجم الطلب + `@ArrayMaxSize` على `telemetry/ingest` + `dto.ts` للمالية (الدفعات).
   - قيد فرادة يمنع تكرار تسوية فترة PPA؛ قيد يمنع حذف `Organization` (تغيير onDelete إلى Restrict).
   - `/health` حقيقي (فحص DB) عبر `@nestjs/terminus`.
6. **لوج منظم**: `nestjs-pino` + معرف طلب + ExceptionFilter عام يوحّد شكل الخطأ ويعالج أخطاء Prisma (P2002...).

### المرحلة M1 — نواة المنصة (3–4 أسابيع)

الهدف: تحويل الثوابت إلى بيانات، والمناداة اليدوية إلى أحداث — هذا أساس «المرونة».

1. **عزل مستأجرين مركزي**: Prisma `$extends` مع `AsyncLocalStorage` يحقن `organizationId` تلقائياً في كل استعلام (مع قائمة استثناءات صريحة)؛ إضافة `organizationId` للجداول العشرة الفاقدة؛ لاحقاً RLS في Postgres كخط دفاع ثانٍ.
2. **وحدة الإعدادات (Settings Module)** — قلب المرونة:
   - ربط الضريبة فعلياً بجدول `TaxCode` في المشتريات وPPA (إزالة `VAT_RATE = 15` الثلاثي) + `taxCodeId` على مستندات المشتريات.
   - **جدول ربط الحسابات (Posting Rules)**: `AccountMapping(purpose → accountId)` بدل النصوص `'1100'` المبعثرة — شرط أساسي ليستخدم أي عميل شجرة حساباته.
   - سلاسل ترقيم قابلة للضبط (قالب بصيغة `{PREFIX}-{YYYY}-{SEQ}`) + **إصلاح ذرّية `next()`** بـ `UPDATE ... RETURNING` حقيقي.
   - إعدادات عامة `OrgSetting(key, value)` للحدود والعتبات (SLA، عتبات PR، سماحية الدفع...).
3. **طبقة الأحداث**: `@nestjs/event-emitter` للأحداث الداخلية + جدول outbox للموثوقية؛ فك التداخلات المضمّنة (تنبيه حرج → حدث → منشئ أمر عمل) تمهيداً لسير العمل والإشعارات والويبهوك.
4. **الجدولة والطوابير**: BullMQ + Redis (أو `pg-boss` لتجنب Redis): توليد الصيانة الوقائية آلياً، النسخ الاحتياطي، وأي عمل ثقيل لاحق (PDF، استيراد).
5. **رموز أخطاء ثنائية اللغة**: كل استثناء يحمل `code` + معاملات؛ الواجهة تترجم بالرمز لا بالـ regex (إحلال تدريجي لـ `errors.ts`).
6. **عقد API مشترك**: توليد OpenAPI عبر `@nestjs/swagger` + توليد أنواع للواجهة (`openapi-typescript`) — يقضي على 86 interface يدوية وانحرافها؛ الويب يستورد `@npi/shared` فعلياً (صلاحيات منمّطة).
7. **ترقيم صفحي موحّد**: DTO استعلام قياسي `{take, skip, search, sort}` وغلاف `{rows, total}` على كل القوائم (النمط موجود في leads — تعميمه).

### المرحلة M2 — استكمال جوهر ERP (4–6 أسابيع)

الهدف: القدرات التي يتوقعها أي مستخدم ERP قبل الحديث عن المرونة.

1. **المرفقات**: نموذج `Attachment` عام (entityType/entityId) + تخزين S3-متوافق (MinIO محلياً) + رفع/معاينة على العقد والفاتورة وأمر العمل والمطالبة.
2. **مركز الإشعارات**: نموذج `Notification` + جرس بعدّاد + تفضيلات؛ تغذيته من طبقة الأحداث (تنبيه حرج، اعتماد مطلوب، فاتورة متأخرة)؛ البريد لاحقاً في نفس البنية (nodemailer + قوالب).
3. **Chatter — سجل النشاط على السجل**: endpoint قراءة لسجل التدقيق + عرضه بذيل كل صفحة تفاصيل + تعليقات المستخدمين (`Comment`) — يحوّل التدقيق المكتوب-فقط إلى قيمة مرئية، ويسد فجوات التدقيق (الأصناف، التيليمتري، الحذف).
4. **طباعة PDF**: الفاتورة الضريبية أولاً (قالب ثنائي اللغة + QR)، ثم العرض والعقد والمستخلص؛ توليد في طابور (Playwright/Puppeteer server-side).
5. **الدائرة المالية المفقودة**: إشعار دائن/مدين بمرجع الفاتورة الأصلية (متطلب ZATCA)، **توزيع الدفعات** (`PaymentAllocation` بين سند القبض وعدة فواتير)، إفراج الاحتجاز على دفعات.
6. **شاشات الإدارة**: `/settings` تضم: المستخدمين والأدوار (CRUD كامل — لا يوجد اليوم أي API لإدارة مستخدم!)، شجرة الحسابات، الضرائب، سلاسل الترقيم، بيانات المنشأة، تغيير كلمة المرور والملف الشخصي.
7. **استيراد/تصدير**: تصدير CSV/XLSX على كل قائمة (المكوّن موجود)، استيراد بقالب + معاينة أخطاء للأصناف والعملاء والموردين وأرصدة الافتتاح.
8. **إعادة هيكلة الواجهة بالتوازي** (تمكينية لكل ما سبق):
   - React Query (كاش، إعادة تحقق، optimistic).
   - مكوّنات `DataTable` (فرز/بحث/ترقيم/تصدير/أعمدة) و`FormModal` (تحقق حقلي بـ react-hook-form + zod من أنواع OpenAPI) — تلغي التكرار في 35 جدولاً و19 نافذة.
   - تعميم `can()` على كل زر إجراء (الإخفاء أو التعطيل مع تلميح).
   - `middleware.ts` للتحقق من الجلسة خادمياً + الانتقال إلى كوكي httpOnly.

### المرحلة M3 — مرونة أودو (6–8 أسابيع)

الهدف: القدرات التي تجعل النظام «يحاكي الأنظمة المتقدمة».

1. **محرك سير العمل**: جدول `WorkflowDefinition/Transition` (من-حالة، إلى-حالة، صلاحية، شرط، إجراءات لاحقة عبر الأحداث) يستبدل سلاسل if في PO/الفاتورة/أمر العمل/المستخلص تدريجياً — يبدأ بكيان واحد (PO) كنموذج ثم يعمم.
2. **سلاسل اعتماد قابلة للضبط**: `ApprovalRule` (كيان + عتبة مبلغ + أدوار متسلسلة) + صندوق «طلبات اعتمادي» + إشعارات — أكثر ما تطلبه المنشآت السعودية فعلياً.
3. **حقول مخصصة**: `CustomFieldDefinition` لكل كيان + عمود `customValues Json` مفهرس (GIN) + عرضها في النماذج والجداول والمرشحات — بديل عملي عن Studio دون هجرة لكل حقل.
4. **طرق العرض**:
   - كانبان بالسحب للفرص (المراحل موجودة) وأوامر العمل.
   - تقويم لأوامر العمل والصيانة الوقائية.
   - عرض قائمة متقدم: مرشحات محفوظة في URL وقابلة للمشاركة، تحديد متعدد + إجراءات جماعية، إعداد أعمدة.
5. **بحث شامل** (Ctrl+K): عبر العملاء/الفواتير/المشاريع/أوامر العمل بفهرس Postgres FTS عربي/إنجليزي.
6. **لوحات ومؤشرات**: مكتبة رسوم (recharts) + لوحة قابلة للتخصيص بالأدوار + حفر تنازلي من المؤشر إلى القائمة المرشّحة.
7. **محرك تقارير خفيف**: طبقة قراءة معرّفة بالبيانات (مصدر + أعمدة + تجميع + مرشحات) تولّد التقارير المحفوظة بدل كتابة كل تقرير يدوياً.
8. **ويبهوك + API عام موثّق** للتكاملات الخارجية (بوابات دفع، مراسلات، محاسبة خارجية).

### المرحلة M4 — التوسع والجاهزية الإنتاجية (6–8 أسابيع، قابلة للتوازي مع M3)

1. **ZATCA فعلي**: onboarding CSID مع فاتورة (بيئة محاكاة الهيئة ثم الإنتاج)، مفاتيح في KMS/HSM، إرسال clearance/reporting حقيقي مع إعادة المحاولة عبر الطابور، وعدّاد ICV رتيب بدل الترتيب الزمني.
2. **تعدد العملات**: جدول `Currency/ExchangeRate` + مبلغ أساس على كل قيد + فروقات صرف.
3. **تعدد الفروع**: بُعد `branchId` على المستندات + سلاسل ترقيم لكل فرع + تقارير مجمّعة (الهيكل الهرمي لـ `Organization` موجود وغير مستخدم).
4. **الفترات المالية**: `FiscalPeriod` + قفل الفترة (منع الترحيل بتاريخ مقفل) + إقفال سنوي إلى الأرباح المبقاة (يتطلب حسابات 3000/5000 المخطط لها).
5. **تسوية بنكية** + استيراد كشف حساب.
6. **موارد بشرية مصغّرة**: موظفون، عُهد، ربط الفنيين بأوامر العمل والتكاليف (بديل `projectManagerId` النصي).
7. **SaaS متعدد المستأجرين**: RLS مفعّلة، تسجيل منشأة ذاتي، فوترة اشتراكات، بيئة staging، رصد كامل (Sentry + metrics + uptime).
8. **تطبيق فني ميداني** (PWA offline-first) لأوامر العمل — مؤجل من المواصفة الأصلية.

## 6. ملاحظات تنفيذية

- **التسلسل ملزم في M0→M1**؛ M2 وM3 يمكن تداخلهما جزئياً؛ M4 عناصر مستقلة تُجدول حسب أولوية العمل (ZATCA الفعلي يتقدم إذا اقترب عميل حقيقي).
- **الاختبارات ليست مرحلة بل عادة**: كل ميزة جديدة من M1 فصاعداً تُسلَّم مع اختباراتها؛ هدف تغطية المنطق المالي 90%+.
- **لا إعادة كتابة**: البنية الحالية (Nest + Prisma + Next) صالحة تماماً للوصول إلى الهدف؛ الخطة كلها إحلال تدريجي strangler-pattern فوق الموجود.
- **خدمتا `procurement` و`fsm`** تُفكَّكان بالتزامن مع M1 (الأحداث تسحب الترحيل المحاسبي إلى المالية، وسير العمل يسحب انتقالات الحالة).
- المدة الإجمالية التقديرية للوصول إلى «مرونة أودو» العملية (نهاية M3): **4–5 أشهر** بوتيرة العمل الحالية، والجاهزية الإنتاجية الكاملة (M4): **6–7 أشهر**.
